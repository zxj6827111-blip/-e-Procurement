## 1. 文档目的

在明确产品边界的前提下，给出一份可执行的整改方向：

1. **说清现状**：哪些已经完成、哪些是预留口子、哪些是本地仍不完整的短板。  
2. **定清方向**：按优先级整改，避免把“外部系统联调”和“本地业务完善”混为一谈。  
3. **定清目标**：内部演示 / 受控试用 / 可售候选 / 正式生产的分级目标与验收口径。

---

## 2. 产品边界（整改前提）

### 2.1 明确不纳入“本地必须做完”的范围

下列能力按设计为 **预留接口 / 适配器契约 / mock 边界**，由客户在实施阶段自行对接真实系统，**不作为本阶段“功能未完成”的主矛盾**：

| 类别 | 说明 |
| --- | --- |
| 统一身份 / SSO | 本地登录 + SSO adapter 边界 |
| OA 外部审批引擎 | 本地 R8 工作流 / 任务 / 消息 |
| ERP / 财务共享 / 银行出款 | 本地结算与资金台账，**不对接真实支付** |
| WMS / 物流平台 | 本地发货、收货、异常 |
| 合同系统 / 电子签章 / CA | 本地合同台账与附件确认 |
| 税控 / 电子发票验真 | 本地发票规则与 adapter 边界 |
| 对象存储 / 杀毒 / 水印 | 本地文件中心；生产需客户基础设施 |
| 生产级数据库 HA | 当前 SQLite 为本地/UAT 过渡 |

### 2.2 本期确认的业务付款口径

**不接入真实付款系统。**  
业务闭环定义为：

```text
验收完成 / 结算资料齐备
  → 财务获得可付依据
  → 财务上传「付款凭证」
  → 系统登记已付款（本地台账）
  → 各方可回看凭证与状态
```

系统职责是：**业务过程管控 + 资料与凭证归档 + 状态可追溯**；  
不是：**银行出款、银企直连、支付网关清算**。

## 3. 现状评估

### 3.1 总体结论

| 维度 | 结论 |
| --- | --- |
| 本地招采主业务闭环 | **主体完成**，可演示、可受控试用 |
| 角色权限与状态机 | **主体完成**，自动化覆盖充分 |
| 外部真实系统联调 | **按设计未实现**，仅为预留口子 |
| 本地付款结案（凭证归档） | **口径已定，产品尚未一等公民化** |
| 正式生产上线 | **NO_GO**（基础设施 + 外部联调 + 安全深度） |

一句话：  
**“不接客户真实外围系统也能跑通阳光采购主业务”已基本成立；本地仍需补齐结算到付款凭证结案的连贯性，并加固安全与数据模型，才能更稳地做受控试用与可售候选。**

### 3.2 已完成能力（本地业务）

| 域 | 现状 |
| --- | --- |
| 需求与审批 | 酒店发起、集团审批、方式判定、建项 |
| 招采过程 | 采购文件、公告邀请、报名资格、报价、截标锁定 |
| 评审定标 | 专家抽取/确认/评分、报告冻结、定标审批、结果通知 |
| 合同订单 | 合同台账、附件、供应商确认、采购订单、收货履约 |
| 结算前端 | 结算材料提交与核验、发票相关能力、模拟资金台账登记 |
| 归档审计 | 档案检查、封档、操作日志、角色只读边界 |
| 商城支线 | 下单、确认、发货、收货、模拟付款确认（独立路径） |
| 工程门禁 | typecheck / 全量 API 测试 / 构建 / OpenAPI / 主流程 E2E 等整体可绿 |

### 3.3 已实测的主链路（证据）

本地主流程 E2E（角色串联 + 页面核验）可跑通至：

```text
酒店需求 → 集团审批 → 招采发布 → 供应商报价 → 专家评分
→ 定标 → 合同确认 → 订单 → 收货/验收 → 结算材料核验
→ 评价 → 归档
```

专项测试另覆盖：R7 结算账单/发票/模拟资金台账、商城收货后模拟付款、权限边界等。

### 3.4 现状问题清单（按性质分类）

#### A. 产品连贯性（本地应完善）

| 编号 | 问题 | 现象 |
| --- | --- | --- |
| P-01 | 结算双路径 | 工作台“结算材料”与 R7“结算财务中心”并存，主故事不清晰 |
| P-02 | 付款结案未成一等公民 | 更偏状态/备注登记，缺少“上传付款凭证即结案”的明确步骤 |
| P-03 | 主流程未闭环到付款凭证 | E2E 停在材料核验，未验证财务上传凭证并标记已付 |
| P-04 | 角色深度不均 | 财务/酒店财务在主链写操作深度弱于经办/供应商/专家 |

#### B. 安全与账号（本地应加固）

| 编号 | 问题 | 现象 |
| --- | --- | --- |
| S-01 | 密码哈希偏弱 | SHA-256 无盐，非慢哈希 |
| S-02 | 登录无限流/锁定 | 可对弱口令在线尝试 |
| S-03 | 演示弱口令规律 | seed 账号 `pass-{userId}` 可预测 |
| S-04 | CSRF / 会话密钥接线不足 | 配置存在，强制落地与密钥用途不完整 |

#### C. 数据与运行（本地应加固）

| 编号 | 问题 | 现象 |
| --- | --- | --- |
| D-01 | 全量 JSON 状态保存 | 并发写存在 last-write-wins 风险 |
| D-02 | 数据库驱动声明超前 | 配置可写 postgres/mysql，运行仍 SQLite |
| D-03 | 对象存储模式写穿本地 | 易造成“已上对象存储”误判 |

#### D. 工程与体验

| 编号 | 问题 | 现象 |
| --- | --- | --- |
| E-01 | Vue + React 双栈 | 长期双份维护成本高 |
| E-02 | 错误提示依赖文案正则 | 后端 message 变更易失效 |
| E-03 | 文档入口分散 | 缺统一根 README / 角色操作闭环说明 |

#### E. 外部预留（不作为本期主整改对象）

| 编号 | 边界 | 说明 |
| --- | --- | --- |
| X-01 | SSO/OA/ERP/WMS/电签/税控/支付 | 契约与 mock 已有，真实联调属客户实施 |
| X-02 | 生产库/对象存储/杀毒/监控 | 属生产基础设施，文档已 NO_GO |

## 4. 整改方向

### 4.1 总原则

1. **边界清晰**：外部系统只做契约完善与对接手册，不假装已联调。  
2. **本地闭环优先**：先把“验收 → 付款凭证 → 已付归档”做成可演示、可验收的本地路径。  
3. **安全先于花样**：试用扩大前先补账号与配置门禁。  
4. **不改业务叙事乱加模块**：优先收口双路径，而不是再开第三条结算体系。  
5. **分级目标验收**：演示 / 试用 / 可售 / 生产分开判定，禁止混用 Go。

### 4.2 整改路线图（建议分四期）

#### 第一期：付款结案产品化（最高优先级）

**目标**：兑现“不接真实付款系统，财务上传付款凭证即可结案”。

| 方向 | 具体内容 |
| --- | --- |
| 业务步骤 | 定义标准步骤：材料齐备/核验 → 财务确认可付 → 上传付款凭证 → 状态=已付款 |
| 资料类型 | 增加或明确 `payment_voucher`（付款凭证）附件类型 |
| 状态绑定 | 凭证上传成功后更新账单/订单/项目侧“已付款”可见状态 |
| 可回看 | 付款进度、履约页、档案可下载/预览凭证 |
| 主路径收口 | 明确工作台材料与结算中心谁做“可付依据”、谁做“付款结案” |
| 验收 | 补一条端到端：收货后到“已付款+凭证可回看” |

**不做**：银行接口、银企直连、自动扣款。

#### 第二期：安全与受控试用加固

| 方向 | 具体内容 |
| --- | --- |
| 密码 | 慢哈希（argon2/bcrypt）+ 盐；迁移旧哈希 |
| 登录防护 | IP/账号限流、失败锁定、临时密码强制修改 |
| 配置门禁 | UAT/生产禁止弱 seed、弱密钥、误开 mock 的硬失败策略 |
| 会话与 CSRF | 明确 Cookie 策略；写操作 CSRF 或自定义头校验 |
| 账号资产 | 演示账号清单不得入库；环境隔离说明写入运维手册 |

#### 第三期：数据一致性与运行可靠性

| 方向 | 具体内容 |
| --- | --- |
| 写路径 | 关键业务实体落表 + 事务，减少整包 JSON 覆盖 |
| 驱动诚实 | 未实现的 DB 驱动 fail-closed，避免运维误配 |
| 文件存储 | object 模式未接通前 readiness 不得宣称生产就绪 |
| 备份 | 本地/UAT 备份恢复手册与定期演练固化 |

#### 第四期：工程收敛与交付体验

| 方向 | 具体内容 |
| --- | --- |
| 前端 | 双栈收敛路线（React 主或 Vue 主二选一，设退场计划） |
| 契约 | 错误码驱动前端提示；共享 DTO 包减少跨包引用 |
| 文档 | 根 README、角色操作手册、付款凭证闭环说明 |
| 性能 | 大 chunk 拆分、关键列表分页与加载体验 |

### 4.3 不改动代码阶段可立即落地的管理动作

即使暂不开发，也可先做：

1. **产品口径冻结**：对外统一“系统外付款 + 系统内凭证归档”。  
2. **验收清单更新**：主流程增加财务“上传付款凭证/登记已付”。  
3. **模块叙事图**：一张图说明工作台结算材料 vs 结算财务中心。  
4. **安全基线清单**：试用前必须关闭的 mock/seed/弱密钥项。  
5. **生产 NO_GO 不改口**：在无客户联调证据前禁止宣称生产 Go。

## 5. 最终目标

### 5.1 目标分层

| 层级 | 最终目标 | 达成标志 |
| --- | --- | --- |
| L1 内部演示 | 全角色可演示阳光采购主故事 | 主流程稳定、文案商业化、无空白页 |
| L2 受控试用 | 客户在隔离环境自助走通主业务 | 含“付款凭证结案”；账号安全达标；备份可恢复 |
| L3 可售候选 | 可作为交付基线投标/签约 | 本地门禁全绿；对接手册齐全；已知限制书面化 |
| L4 正式生产 | 客户生产环境可上线 | 真实外围联调完成 + 生产库/存储/安全/运维达标 |

当前合理定位：**L1 已基本达到；冲刺 L2；L3 有条件；L4 未达标。**

### 5.2 本地业务最终态（不含真实外部系统）

```text
需求 → 审批 → 建项 → 招采 → 报价 → 评审 → 定标
  → 合同确认 → 订单 → 收货/验收
  → 结算资料齐备并核验
  → 财务上传付款凭证并登记已付
  → 评价 / 归档 / 审计可追溯
```

**最终态特征：**

1. 主路径单一、角色任务清晰。  
2. 付款不依赖外部支付系统，但**凭证必留、状态必清、责任可追**。  
3. 权限、审计、附件、状态机在本地完整。  
4. 外部系统仅以“对接点”存在，不阻断本地闭环演示与试用。

### 5.3 生产最终态（含客户实施）

在 L2/L3 基线之上，客户完成：

- SSO / 组织同步  
- 必要的 OA/ERP/合同/发票/仓储对接（按合同范围）  
- 生产数据库、对象存储、杀毒、监控备份  
- 安全测试与运维 Runbook  

才可判定 **Production Go**。

### 5.4 成功度量（建议）

| 指标 | L2 目标示例 |
| --- | --- |
| 主流程 E2E | 新建需求 1 条，100% 跑到“已付款+凭证可回看+可归档” |
| 角色验收 | 12 角色菜单与关键写权限抽检通过 |
| 安全 | 无限流弱口令问题关闭；生产误配 fail-closed |
| 缺陷 | P0/P1 打开项为 0；付款路径无阻断级缺陷 |
| 文档 | 操作手册含付款凭证步骤；限制清单已签字确认 |

## 7. 风险与约束

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 把模拟付款说成真实支付 | 商务与合规风险 | 统一话术：系统外付款 + 凭证归档 |
| 双路径并存导致培训成本高 | 用户不知道点哪 | 第一期强制收口主入口 |
| 过早宣称生产就绪 | 交付翻车 | 坚持分级 Go/No-Go |
| 只补 UI 不补状态与审计 | 凭证上传了但不可追溯 | 付款结案必须带状态、附件、审计日志 |
| 安全债拖到扩面试用 | 账号被撞 | P1 与扩面试用绑定 |

## 8. 建议的近端行动（2～4 周，方案级）

1. **冻结付款口径**（本文 2.2）为正式产品定义。  
2. 产品输出《付款凭证闭环 PRD》一页纸：角色、前置条件、附件、状态、页面入口。  
3. 研发评估现有接口能否扩展（结算材料类型 / 资金台账附件 / 已付状态），给出最小改造面。  
4. 测试补“合同后→验收→付款凭证→已付”专项用例（API + 浏览器）。  
5. 安全出《受控试用放行检查表》。  
6. 更新客户材料：能力清单、限制清单、对接预留清单分离表述。

## 9. 最终总结

### 现状

- 本地阳光采购**主业务已基本完成**，主链路可跑通到归档。  
- 真实外围系统**按设计预留**，不应算作“业务没做完”。  
- 本地短板集中在：**付款结案产品化、结算路径收口、安全、数据可靠性、工程收敛**。

### 整改方向

- **先做本地付款凭证闭环**，落实“财务上传凭证即可，不接真实付款系统”。  
- **再做安全与试用门禁**，保障扩面试用。  
- **再做数据与工程收敛**，提升可维护与可扩展。  
- **外部联调单独项目化**，不阻塞本地业务收口。

### 最终目标

- **短期**：受控试用可用的完整本地闭环（含付款凭证结案）。  
- **中期**：可售候选基线（文档、限制、门禁、对接手册齐全）。  
- **长期**：客户实施完成后进入正式生产 Go。
