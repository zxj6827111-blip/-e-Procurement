# 酒店采购流程规范化小模块最终实施改造方案

评估日期：2026-06-24

适用工程：`E:\Software Development\‌e-Procurement`

参考资料：

- 客户演示稿：`白天鹅连锁酒店供应链项目演示 - 202506.pdf`
- 当前工程代码：Express API + Vue Web
- 当前工程文档、OpenAPI、API 测试与本地构建结果

## 1. 评估结论

当前客户的核心诉求应收敛为：

> 在现有酒店供应链/采购流程中补齐一个“采购招采规范化小模块”，重点解决供应商准入、询价/应标、评标/定标、结果审批、履约评价和过程留痕不规范的问题。

不建议把本次对外表述为“重建完整酒店供应链平台”或“完整电子招投标交易平台”。PDF 中确实出现了商城选品、商品下单、订单支付、退货、资金授信、样板间、开业包等更宽的供应链/商城能力，但客户当前明确问题是“招投标不规范”。因此本次应做一次性交付的小模块闭环，而不是把 PDF 中所有供应链页面都纳入本次开发。

当前工程已有较完整的 MVP 骨架：供应商、采购需求、项目、报价、评审、定标、合同履约、评价、档案、审计、OpenAPI 和 API 测试均已存在，且本次验证通过。但它仍是 Mock/Seed 驱动的演示工程，存在权限旁路和生产化缺口，不能直接作为“完整闭环可上线系统”验收。

最终建议：

- 对客户验收口径：一次性交付“酒店采购招采规范化小模块闭环”。
- 对开发组织口径：按工作流分工并行推进，但不再对客户拆“几期”。
- 对上线判断：当前工程可作为改造基线，尚不可直接 Go-Live；必须先修复权限、安全、数据持久化、中文显示、前端工作台和关键测试缺口。

- 系统主名称使用“询价/比选项目”“招采项目”“采购规范化项目”。

- 对外避免默认称为“完整电子招投标交易平台”，防止客户误解为具备 CA、电子签章、投标加密、开标解密、公共资源交易等能力。

## 6. 最终建设范围

### 6.1 纳入本次一次性交付的小模块闭环

本次应交付以下完整闭环：

```text
供应商注册/登记
-> 资质初审
-> 准入评估
-> 合格供应商库
-> 供货区域与授权品类
-> 采购申请
-> 采购审批
-> 询价/比选项目
-> 邀请供应商
-> 供应商应标/报价/答疑/资料上传
-> 报价截止锁定
-> 报价对比
-> 评审/评标
-> 定标审批
-> 生成采购订单
-> 供应商确认订单
-> 收货验收
-> 异常处理
-> 供应商评价
-> 发票/送货单/验收单等结算资料上传
-> 项目归档
-> 审计查询
```

### 6.2 明确不纳入本次

以下内容不做，避免从“小模块”膨胀成完整供应链/电商/交易平台：

- 完整商城、购物车、商品下单和订单支付。
- 商品运营、产品上架、销售定价、定价报告。
- 余额、授信、充值、付款、财务核算。
- CA 认证、电子签章、投标文件加密、开标解密、远程评标。
- 区块链存证、AI 串标分析。
- ERP/WMS/OA/财务/合同系统正式联调。
- 外部交易备案作为主模块，除非客户明确这是当前高频流程。

## 9. 权限与安全整改

当前工程权限设计方向正确，但存在必须修复的旁路。以下是上线前 No-Go 项：

| 风险 | 当前问题 | 必须整改 |
|---|---|---|
| 审计日志接口开放 | `/api/audit-logs` 等接口缺少角色和范围判断，供应商可读 | 仅审计/纪检、授权管理角色可按范围只读；供应商、专家、管理员默认禁止 |
| 合同总表开放 | `/api/contracts` 未完整按角色/项目/组织过滤，管理员可读合同 | 增加统一 `assertReader`，管理员禁止读取业务合同内容 |
| 专家旁路看报价 | 专家可通过 `/projects/:id/bids/summary` 在截止后读取完整报价 | 专家必须经过评审任务、保密确认和授权视图，不可直接走报价 summary |
| 管理员可读采购需求 | `/procurement-requests/:id` 对管理员开放 | 管理员仅维护系统配置，不读取业务明细 |
| 配置接口裸露 | `/roles`、`/role-permissions`、`/system-dictionaries` 等对低权限开放 | 明确哪些为公共基础数据，哪些仅管理员可见 |
| OpenAPI 校验弱 | 仅字符串匹配路径 | 校验 method、schema、status code、security，并检查运行时未文档化接口 |
| Mock Header 鉴权 | `x-mock-user-id` 直接信任 | 演示可保留，但验收文档必须声明生产认证未接入；生产前接 SSO/真实登录 |

角色边界：

| 角色 | 应允许 | 应禁止 |
|---|---|---|
| 采购经办人 | 发起采购申请、创建项目、邀请供应商、截止后查看授权报价、发起定标、订单收货 | 截止前查看报价金额/响应文件、修改专家评分、越权查看非经办项目 |
| 采购管理人 | 审批采购申请、审批定标、查看看板、维护准入规则 | 绕过审批直接定标、截止前查看报价明细 |
| 供应商 | 维护本企业资料、参与报价、确认订单、上传结算资料 | 查看其他供应商任何明细 |
| 审计/纪检 | 只读查看项目、档案、日志、异常操作 | 修改业务数据 |
| 系统管理员 | 维护用户、角色、组织、字典、菜单 | 查看报价金额、定标理由、供应商评价、审计实质内容 |

## 10. 接口改造方向

后端保持 Express，不引入大型新框架。建议按现有路由分层演进：

| 路由/模块 | 改造重点 |
|---|---|
| `supplier-routes.ts` | 补资质初审、准入评估、供货区域、封样、限制名单生命周期 |

## 11. 前端改造方向

前端保持 Vue，不引入大型框架。当前页面较多但分散，建议围绕“项目详情工作台”重组。

### 11.1 必须补齐的页面体验

- 列表：筛选、状态标签、空状态、错误提示。
- 表单：必填校验、附件占位、保存/提交/撤回/重提。
- 详情：统一项目工作台，分 tab 展示流程节点。
- 操作：按钮按角色和状态显示，不仅菜单隐藏。
- 敏感数据：报价金额、文件名、响应文件、评分意见按角色动态脱敏。
- 审计日志：关键动作返回日志号，页面可展示。
- 中文乱码：修复页面和 seed 数据的中文显示问题，统一 UTF-8。

### 11.2 页面结构建议

## 12. 测试与验收要求

现有测试通过，但必须新增以下测试后才能作为最终验收依据。

### 12.1 API 测试

- 供应商准入主流程测试。
- 采购申请到询价/比选项目测试。
- 供应商报价提交、撤回、重提测试。
- 报价截止前保密测试，断言响应体不含 `amount`、`fileName`、`responseFileMetadata`。
- 报价截止后比价测试。
- 专家/评审用户不可绕过保密确认直接读报价测试。
- 定标审批和订单生成测试。
- 采购订单确认、部分收货、全部收货、异常收货测试。
- 供应商评价和结算资料上传测试。
- 供应商数据隔离测试。
- 审计只读权限测试。
- 管理员不可读业务实质内容测试。
- 项目档案完整性和补充资料申请测试。
- 配置接口权限矩阵测试。

### 12.2 OpenAPI 校验

升级 `scripts/validate-openapi.mjs`：

- 校验路径和 method。
- 校验关键 request/response schema。
- 校验 403、404、400 等错误响应。
- 校验需要鉴权的接口有 security 或等效说明。
- 校验运行时接口不能漏出未文档化路径。

### 12.3 前端验证

至少完成以下浏览器验证：

- 采购经办人从采购申请到项目创建。
- 供应商只看到本企业项目并提交报价。
- 采购方截止前只能看提交状态，不能看金额和文件。
- 截止后采购方查看比价并发起定标。
- 非最低价中选必须填写理由。
- 订单确认、收货异常、评价、结算资料上传。
- 审计用户只读查看全流程。
- 系统管理员无法进入业务实质页面。

## 16. 最终 Go/No-Go 判断

| 判断项 | 结论 |
|---|---|
| 是否符合 PDF 中招采规范化主链 | 基本符合 |
| 是否覆盖客户“小模块规范招投标流程”诉求 | 方向符合，但需收口 |
| 当前代码是否可作为开发基线 | 可以 |
| 当前代码是否可直接上线验收 | 不可以 |
| 是否建议继续按“全平台一次性交付”推进 | 不建议 |
| 推荐最终实施口径 | 一次性交付“酒店采购招采规范化小模块闭环” |

最终结论：

> 当前工程适合作为小模块改造基线。下一步不应继续扩写“大而全平台方案”，而应先完成权限整改、数据对象补齐、项目详情工作台重组、采购订单/收货/结算资料对象化、OpenAPI 契约增强和核心验收测试。完成这些后，再按一次性交付口径提交客户演示和验收。
