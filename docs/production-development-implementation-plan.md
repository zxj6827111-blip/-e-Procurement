# 酒店采购规范化系统正式开发实施方案

版本: V1.0  
日期: 2026-06-24  
适用工程: `E:\Software Development\‌e-Procurement`

## 1. 文档目标

本文用于把当前演示工程转化为正式可开发、可排期、可验收的实施方案，服务于以下目标:

- 明确一期正式建设范围与非范围。
- 明确当前工程与正式系统之间的差距。
- 明确推荐技术路线、模块拆分、实施顺序和验收口径。
- 为后续研发排期、资源投入、联调准备和上线评审提供依据。

本文不是客户演示稿，也不是纯技术预研结论。本文默认目标是: 在现有工程基础上，逐步落地一个可正式使用的酒店采购规范化系统。

## 2. 项目定位

### 2.1 建设定位

本项目一期定位为:

**国企酒店集团内部使用的采购规范化与过程留痕系统**

核心目标不是建设完整商城，也不是建设法规级电子招投标交易平台，而是把酒店集团当前采购流程中的以下关键环节做成可用系统:

- 供应商注册、准入、资质与封样管理
- 采购申请与项目发起
- 询价 / 比选 / 招标过程管理
- 供应商报名、应标、报价、答疑、资料上传
- 报价截止锁定与保密控制
- 专家评审、比价报告、定标审批
- 采购订单、收货验收、异常处理
- 供应商评价、结算资料上传
- 项目归档与审计追溯

### 2.2 一期明确不做

以下内容不纳入一期正式范围:

- 商城选品、购物车、商品下单、订单支付
- 酒店资金余额、授信、充值、财务清算
- 完整物流发货平台
- 退货交易平台化闭环
- CA、电子签章、投标文件加密解密、开标大厅、可信时间戳、防篡改存证
- 公共资源交易平台级能力
- 将 OA / ERP / 财务 / 合同系统完全替代为本系统

这些能力可在后续阶段评估，但不能与一期采购规范化主链混做。

## 3. 当前工程现状

当前仓库已经不是空壳，具备较完整的演示型业务骨架，但还不是正式系统。

| 维度 | 当前现状 | 当前问题 | 正式建设方向 |
|---|---|---|---|
| 前端 | 已有 Vue 页面、工作台、角色视角 | 偏演示，缺少正式登录与真实上传交互 | 保留现有页面骨架，按正式流程收敛 |
| 后端 | 已有 Express 路由、权限规则、OpenAPI、测试 | 运行态仍基于 seed / mock | 保留现有 API 结构，逐步替换为正式实现 |
| 数据 | 已有完整 seed 场景数据 | 内存态，不持久化 | 接入正式数据库 |
| 登录 | `mock-login`、`mock-role-switch`、请求头身份 | 不具备正式认证与会话安全 | 接入真实登录或企业 SSO |
| 角色 | 已有角色矩阵和权限测试 | 仍可在同一界面切换身份 | 正式系统按账号、组织、角色授权运行 |
| 上传 | 多处仅保存文件名或 metadata | 公告、资质、图片、响应文件、结算资料无法真实留存 | 建正式文件服务与上传下载能力 |
| 审批 | 已有 mock 审批动作和状态 | 不能作为正式审批链使用 | 建立正式审批流或审批适配器 |
| 审计 | 已有审计日志模型和演示接口 | 仍需补强正式追责、查询范围和不可篡改性 | 完整审计留痕与查询控制 |
| 测试 | 已有 API 测试、类型检查、构建、OpenAPI 校验 | 缺少正式 E2E、上传、安全、联调验证 | 扩展到生产级验证链路 |
| 运维 | 本地可跑通 | 缺少环境隔离、部署、监控、回滚 | 建立正式部署与发布流程 |

## 4. 推荐实施路线

### 4.1 推荐方案

推荐采用:

**在现有 `Vue + Express + TypeScript` 工程上渐进式生产化改造**

推荐理由:

- 当前仓库已经有完整业务边界、路由结构、权限规则、OpenAPI 和测试，不适合推倒重来。
- 用户当前诉求是“把系统真正做成可用功能”，不是重新做一套全新方案。
- 现有代码已覆盖供应商、采购、报价、评审、定标、订单、收货、档案、审计等主链，适合作为正式实现基线。
- 渐进式改造可以保留现有测试资产和页面原型，降低重写成本。

### 4.2 不推荐方案

不推荐当前阶段重做一套全新后端框架或重做全新前端系统，原因如下:

- 会丢失现有业务规则沉淀和测试沉淀。
- 会把问题从“正式化落地”变成“重新造工程骨架”。
- 会推迟真正的业务闭环交付时间。

## 6. 目标系统架构

### 6.1 逻辑架构

| 层级 | 目标能力 | 说明 |
|---|---|---|
| Web 前端 | 业务页面、工作台、表单、上传、权限显示 | 保留现有 Vue 路线 |
| API 服务 | 认证、业务规则、权限控制、审计留痕、上传下载、流程流转 | 保留现有 Express 路线 |
| 数据库 | 业务主数据、流程状态、附件元数据、日志 | 正式持久化 |
| 文件存储 | 公告、图片、资质、响应文件、发票、验收单等 | 本地文件服务或对象存储 |
| 认证层 | 本地账号体系或集团 SSO | 一期必须落地其一 |
| 审批与集成 | OA / ERP / 合同 / 财务 / 消息适配层 | 一期允许部分适配，逐步联调 |
| 运维层 | 环境配置、日志、监控、备份、发布、回滚 | 正式上线前必须具备 |

### 6.2 数据架构原则

- 业务数据与演示 seed 数据彻底分离。
- 所有核心对象必须有主表、状态字段、操作人、操作时间。
- 所有上传文件必须区分“文件实体”和“业务引用关系”。
- 所有审批、驳回、重提、锁定、解锁、归档、补档都必须形成审计记录。
- 供应商、采购方、专家、审计、管理员的数据可见范围必须由服务端强校验。

## 7. 核心模块拆分

### 7.1 基础与权限模块

范围:

- 用户、组织、岗位、角色
- 菜单、按钮、接口权限
- 登录、登出、会话
- 数据范围控制
- 审计日志

关键建设点:

- 去掉 `mock-role-switch` 作为正式入口
- 正式账号登录或企业 SSO 登录
- 基于账号的角色授权，而不是页面内自由切换身份
- 服务端统一 `RBAC + Data Scope` 校验

## 8. 分阶段实施计划

### 阶段 0: 范围冻结与正式化设计

周期建议: 1-2 周

交付物:

- 正式建设范围冻结
- 页面清单冻结
- 数据对象清单冻结
- 权限矩阵冻结
- 审批链与字典项确认表

验收标准:

- 客户 / 业务 / 实施三方确认一期范围
- 明确哪些规则可配置，哪些规则固定
- 明确非范围能力不进入一期开发

### 阶段 1: 生产底座建设

周期建议: 3 周

建设内容:

- 数据库接入
- 账号登录 / 会话体系
- 文件上传下载中心
- 审计日志落库
- 环境配置分离
- 基础配置页

交付物:

- 可登录正式系统
- 数据重启后不丢失
- 公告、图片、资质文件可真实上传留存

验收标准:

- 创建的数据重启后仍存在
- 不同账号登录仅能看到自身权限范围
- 上传文件可预览、下载、审计追溯

### 阶段 2: 供应商与采购申请主链

周期建议: 3-4 周

建设内容:

- 供应商注册、初审、准入、封样、授权品类、供货区域
- 采购申请、采购明细、申请附件、审批、项目发起

交付物:

- 可从供应商准入走到采购项目创建

验收标准:

- 供应商资料、图片、附件真实留存
- 采购申请审批后可生成项目
- 管理端与供应商端权限隔离有效

### 阶段 3: 应标、报价、评审、定标主链

周期建议: 4 周

建设内容:

- 公告 / 邀请 / 报名
- 应标 / 报价 / 答疑 / 资质文件上传
- 截止锁定
- 专家评审
- 比价报告
- 定标审批

交付物:

- 可从项目发布走到定标审批完成

验收标准:

- 截止前保密规则由服务端严格控制
- 供应商只能看到本企业数据
- 专家只能看到自身评审任务
- 定标审批链可真实流转并留痕

### 阶段 4: 订单、收货、评价、结算资料、归档

周期建议: 3-4 周

建设内容:

- 采购订单生成与确认
- 收货验收与异常登记
- 供应商评价
- 发票 / 送货单 / 验收单上传
- 项目归档、补档、审计查询

交付物:

- 形成从采购申请到归档的正式闭环

验收标准:

- 订单状态与收货状态可持续追踪
- 结算资料真实上传并可审计
- 项目归档可检查完整性

### 阶段 5: 联调、UAT 与上线准备

周期建议: 2-3 周

建设内容:

- OA / ERP / 合同 / 消息等必要接口联调
- UAT
- 数据初始化
- 培训与上线预演
- 上线切换与回滚方案

交付物:

- 上线包
- UAT 问题关闭清单
- 试运行方案

验收标准:

- 主流程全量通过
- 无阻断性权限缺陷
- 无阻断性上传、留存、审批、归档问题

## 9. 数据库与文件落地建议

### 9.1 数据库对象优先级

第一批必须正式建表:

- users
- organizations
- roles

- suppliers
- supplier_qualifications
- supplier_reviews
- supplier_regions
- supplier_categories
- sample_records
- procurement_requests
- procurement_request_items
- projects
- announcements
- invitations
- registrations
- bids
- bid_items
- bid_attachments
- expert_assignments
- scoring_sheets
- comparison_reports
- award_approvals
- purchase_orders
- receipt_records
- supplier_evaluations
- settlement_materials
- archive_items
- audit_logs
- files
- file_versions

### 9.2 文件落地原则

- 所有上传文件统一生成 `file_id`
- 业务表只关联 `file_id` 或业务-文件关系表
- 支持版本替换，不直接覆盖历史文件
- 删除采用业务软删除和文件引用计数，不做无痕物理删除
- 下载必须服务端鉴权，不能直接暴露文件真实路径

## 10. 认证、角色与页面策略

### 10.1 登录策略

一期必须二选一:

- 本地正式账号体系
- 集团 SSO 登录

如果 SSO 暂时无法联调，允许先上本地账号体系，但必须保留后续切换 SSO 的适配层。

### 10.2 角色策略

正式系统保留以下角色:

- 集团采购管理人员
- 采购经办人
- 供应商用户
- 评审专家
- 纪检 / 审计人员
- 系统管理员

正式系统不保留“同一界面任意切换角色”的演示模式。

### 10.3 页面策略

- 采购方走“项目详情工作台”主入口
- 供应商走“供应商门户”
- 专家走“评审任务入口”
- 审计走“只读审计入口”
- 管理员只进基础配置，不进入业务工作台

## 11. 测试与验收方案

### 11.1 必测项

- 单元测试: 规则、状态流转、权限判断
- API 集成测试: 认证、上传、主流程、错误分支
- E2E 测试: 采购方、供应商、专家、审计、管理员五类角色
- 文件测试: 上传、预览、下载、替换、删除、权限拦截
- 安全测试: 越权、伪造身份、未授权下载、接口直连
- 回归测试: 主流程与关键历史缺陷

### 11.2 正式验收口径

一期验收至少满足:

- 数据可持久化
- 文件可真实上传留存
- 正式登录可用
- 角色隔离有效
- 从采购申请到归档可完整走通
- 审计日志可查
- 主流程无阻断缺陷

## 12. 团队与资源建议

建议最小配置:

- 1 名产品 / 实施负责人
- 1 名业务分析 / 验收对接
- 2 名后端开发
- 2 名前端开发
- 1 名测试
- 1 名兼岗运维 / 部署支持

如果需要同时做真实集成联调，建议额外增加 1 名接口联调负责人。

## 13. 风险与依赖

### 13.1 主要风险

- 客户范围持续扩张，把商城、支付、资金等内容重新压回一期
- 审批链、组织权限、采购规则迟迟不冻结
- SSO、OA、ERP、合同、财务接口资料不齐
- 文件服务选型过晚，导致上传类功能整体阻塞
- 供应商历史数据、组织人员数据缺乏初始化方案

### 13.2 关键依赖

- 一期范围确认
- 角色与组织边界确认
- 审批链确认
- 附件分类与归档目录确认
- 外部系统接口资料
- 测试账号和测试环境准备

## 14. 建议的立即动作

建议按以下顺序立即推进:

1. 冻结一期范围，签字确认非范围项。
2. 冻结角色矩阵、审批链、归档目录、附件分类。
3. 输出数据库表设计和文件存储设计。
4. 先启动阶段 1 生产底座改造。
5. 底座通过后，再按阶段 2-4 推进主链开发。

## 15. 最终判断

当前仓库可以作为正式建设基线，但不能直接上线。

正式开发应采用“保留现有工程骨架、先补生产底座、再完成采购主链”的路线，而不是继续维持演示模式，也不是推倒重写。
